**ID**: `cpt-cf-oagw-adr-cors`

**Priority**: p4

## Context and Problem Statement

OAGW proxies requests to upstream services. When web browsers make cross-origin requests, CORS policies are enforced. Without proper CORS support, browser-based clients cannot use OAGW. Key challenges: CORS is browser-specific, preflight OPTIONS must be handled locally (not proxied), CORS headers vary per upstream, credential-bearing requests require strict origin matching, and overly permissive CORS exposes APIs to unauthorized origins.

## Decision Drivers

* Support browser-based clients (SPAs, web apps)
* Security: prevent unauthorized cross-origin access
* Flexibility: per-upstream/route CORS configuration
* Performance: minimize preflight overhead
* Standards compliance: RFC 6454, WHATWG Fetch spec

## Considered Options

* Proxy CORS to upstream (passthrough)
* CORS as guard plugin
* Built-in CORS handler (first-class feature)

## Decision Outcome

Chosen option: "Built-in CORS handler", because it provides fast preflight handling, works when the upstream is unavailable, and avoids plugin ordering complexity.

**Rationale**:

1. **Performance**: Preflight handled immediately, no upstream round-trip
2. **Reliability**: Works even if the upstream is down or does not support CORS
3. **Simplicity**: Clear configuration model, no plugin ordering complexity
4. **Security**: OAGW-level origin enforcement happens before a request reaches the upstream
5. **Standards**: Proper CORS implementation per the WHATWG Fetch spec

Options 1 and 2 are rejected: proxying adds latency and fails when the upstream is unavailable; the guard-plugin approach introduces ordering issues and a more complex configuration surface.

### Preflight Request Handling

Browser preflight requests carry no credentials (per WHATWG Fetch spec), so no tenant context is available for upstream resolution. The handler detects a CORS preflight (OPTIONS + Origin + Access-Control-Request-Method) and returns a **permissive 204 No Content** that echoes back the requested origin, method, and headers — no upstream resolution and no body. Origin and method enforcement is deferred to the subsequent actual request.

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400
Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers
```

Preflight requests bypass per-request auth and plugin checks but remain subject to infrastructure-level controls (global/edge rate limiting, WAF/DDoS protection).

### Actual Request Handling

On the actual request, after upstream resolution (tenant context from the authenticated request), the origin is validated against the upstream's CORS configuration before forwarding: an origin not in `allowed_origins` is rejected with `403 Forbidden` (GTS type `gts.cf.core.errors.err.v1~cf.oagw.cors.origin_not_allowed.v1`), and a method not in `allowed_methods` is rejected with `403 Forbidden` (GTS type `gts.cf.core.errors.err.v1~cf.oagw.cors.method_not_allowed.v1`). Allowed requests proceed and receive CORS response headers (`Access-Control-Allow-Origin`, `Access-Control-Expose-Headers`, `Access-Control-Allow-Credentials`).

### Origin Matching

Origins are matched by **exact string match** (protocol-sensitive and port-sensitive) against `allowed_origins`; `*` matches any origin. No regex patterns are supported — this prevents bypasses such as `https://evil.com.example.com`. `allow_credentials: true` is incompatible with the wildcard origin and is **rejected at configuration validation time**. `Vary: Origin` is always included to prevent cache poisoning. CORS is **disabled unless explicitly enabled** (deny by default).

### Hierarchical Configuration

CORS configuration follows the sharing modes. With `inherit`, a child's origins are **unioned** with the parent's origins (union semantics). With `enforce`, a child cannot add origins.

### Consequences

* Good, because browser-based clients can use OAGW
* Good, because fast preflight handling (no upstream round-trip)
* Good, because works when the upstream is unavailable
* Good, because secure by default (disabled unless configured)
* Good, because standards-compliant implementation
* Bad, because adds built-in logic to the OAGW core
* Bad, because requires CORS configuration for each upstream/route needing browser access
* Neutral, because CORS only affects browser clients (other clients unaffected)
* Neutral, because preflight requests bypass per-request auth/plugin checks (by design) but still pass through global/edge rate limiting and WAF/DDoS controls

### Confirmation

Integration tests verify: preflight returns a permissive 204 with echoed CORS headers; actual requests include CORS response headers for allowed origins; disallowed origins are rejected with 403 on actual requests; disallowed methods are rejected with 403 on actual requests; `allow_credentials` with a wildcard origin is rejected at validation time.

## Pros and Cons of the Options

### Proxy CORS to upstream

Forward all requests, including OPTIONS, to the upstream.

* Good, because simple (no OAGW logic), upstream controls CORS
* Bad, because preflight adds round-trip latency
* Bad, because the upstream may not support CORS
* Bad, because cannot enforce OAGW-level origin restrictions
* Bad, because preflight fails if the upstream is unavailable

### CORS as guard plugin

Implement CORS as a configurable guard plugin.

* Good, because flexible per-upstream/route configuration
* Good, because local preflight handling
* Good, because can enforce stricter CORS than the upstream
* Good, because works even if the upstream is down
* Bad, because plugin ordering issues (must run before all other plugins)
* Bad, because more complex configuration

### Built-in CORS handler

CORS as a first-class feature handled before the plugin chain.

* Good, because preflight is handled before routing/auth/plugins (fast path)
* Good, because clear configuration model, no plugin ordering issues
* Good, because standards-compliant default behavior
* Bad, because adds built-in logic, not extensible via plugins (but can be overridden)

## More Information

| Criteria | Proxy | Plugin | Built-in |
|---|:---:|:---:|:---:|
| Preflight latency | High | Low | Low |
| Configuration complexity | None | Medium | Low |
| Upstream independence | No | Yes | Yes |
| Plugin ordering issues | N/A | Yes | No |
| Standards compliance | Depends | Yes | Yes |
| Works when upstream down | No | Yes | Yes |
